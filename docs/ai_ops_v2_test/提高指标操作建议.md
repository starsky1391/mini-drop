# 提高 ai_ops_v2 评测指标 —— 操作建议

> 依据：90 轮审计包逐包分析（live-vm-v9-official-20260811）
> 当前成绩：严格根因 46.7%、平均分 78.61、abstention 100%、unsafe 0

---

## 一、先看整体：哪些分丢了

90 轮里 46 轮未命中严格根因，失分分布集中在两个维度：

1. **根因维度（40 分/项）**：未命中案例几乎都丢在这里 —— 或 abstain 判证据不足，或定位错（同宿主 vs 下游）。
2. **证据维度（25 分/项）**：失分来源是「未采集 oracle 要求的采集器」和「证据引用无效」，是**采集计划问题而非推理问题**。
3. **轨迹维度（20 分/项）**：已经很强（100% 覆盖，未命中案例也拿 15-20 分），不是瓶颈。

结论：**把精力花在「让该采集的探针被采到」和「补下游/根因实体分析」上，收益最大。**

---

## 二、优先级最高的三类改进（预期直接提升严格根因率）

### 1. 探针选择策略：运行时类症状必须触发 `runtime_snapshot` 采集 ⭐⭐⭐

**现状（最严重的系统性缺口）**：

| 案例 | 平均分 | 系统实际采集 | oracle 要求 |
|---|---|---|---|
| GO-LOCK | 48.4 | sys_metrics+log_scan+perf_cpu | **runtime_snapshot** |
| RUNTIME-STALL | 49.8 | sys_metrics+log_scan+perf_cpu | **runtime_snapshot** |
| LATENCY | 52.6 | sys_metrics+log_scan | **runtime_snapshot** |
| **PYTHON-LOCK（对照）** | **94.7** | **runtime_thread_snapshot**+sys_metrics | runtime_snapshot ✅ |

同一个「运行时锁/停顿」故障，Python 案例正确采集 `runtime_thread_snapshot` 并识别为 `runtime_lock_contention`，Go 案例却因为没采 runtime_snapshot 而 abstain。**差异 100% 在探针选择**，不是分析能力。

**操作**：
- 在 `choose_probe_ids(symptom)` 或症状→探针映射里，把「锁竞争 / 运行时停顿 / 延迟飙升」类症状的 R1 探针计划加入 `runtime_thread_snapshot`（对应 `runtime_snapshot` 采集器）。
- 关键在 `run_ai_ops_v2_vm.py` 的 `create_and_run` 里 `choose_probe_ids(intent.symptom)` 这一段（`orchestrator.py:281` 附近有相关逻辑）。确认 `runtime_stall`、`lock_contention` 症状会映射到该探针。
- 预期：GO-LOCK / RUNTIME-STALL / LATENCY 三个案例从 ~50 分 → 90+ 分，严格根因率 +3 案例。

### 2. 下游依赖分析与可达性探测 ⭐⭐⭐

**现状**：`payment_pause_v1`（docker pause paymentservice）和 `noisy_downstream_v1` 都是下游故障，但系统：
- PAYMENT 判 `insufficient_evidence`（46.0 分）
- NOISY-DOWNSTREAM 误判为同宿主 I/O 争用（44.2 分）

系统没有「下游可达性」证据来源，也没有把 `docker pause` 这类下游不可达归因到依赖关系。

**操作**：
- 增加一个「下游可达性探测」探针（如对目标服务的 downstream 依赖做 TCP/HTTP 探活），采集器归入诊断的 evidence。
- 在 `domain_analyzers` / `assess_cluster` 里补「下游依赖不可达」的归因路径：当目标自身指标正常、但其依赖服务不可达时，根因定位到 downstream。
- `noisy_downstream` 需要区分「本机 CPU 噪声（same_host）」与「下游被 pause（downstream）」两个根因同时成立 → 补复合故障归因。
- 预期：PAYMENT 46→85+，NOISY-DOWNSTREAM 44→70+，严格根因率 +2 案例。

### 3. 根因实体（root_entity）识别 ⭐⭐

**现状**：仅 2 个案例指定根因实体（`paymentservice`、`redis-cart`），全部未命中（0/2）。这是最直接的独立短板，也是「根因实体命中」指标唯一的分数来源。

**操作**：
- 在结论的 `cluster_assessment.root_entity` 字段填入具体服务名。目前该字段普遍为 `None`。
- 方式：`assess_cluster` 或结论生成阶段，把 `root_location.target_ref` 对应的服务名/容器名解析出来填进去；下游类填依赖服务名，宿主类填 host，自身类填目标服务名。
- 预期：root_entity 0/2 → 2/2，且 PAYMENT/REDIS 案例的分类分上升。

## 三、次优先改进

### 4. 重复一致性（36.7% → 目标 60%+）

90 轮里相同案例不同重复的输出一致率仅 36.7%，说明同一故障在不同轮次结论漂移大。来源：模型调用随机性 + 探针复用策略（`MINI_DROP_DIAGNOSIS_REUSE_MAX_AGE_SECONDS=0` 已关闭复用）导致每轮证据略不同。

**操作**：对高确定性信号（如 OOM、enospc、进程锁）优先走规则引擎而非 LLM 兜底；对 LLM 输出加温度收敛或多数投票。这项不直接加严格根因分，但对「评测可信度」很重要。

### 5. 证据引用完整性（5 分/项）

部分案例因 `cited_refs` 为空或引用无效证据扣 5 分（如 GO-LOCK 21/25、RUNTIME-STALL 22.3/25、CONFLICT 5/25）。CONFLICT 案例 5/25 是因为 abstain 时不引用任何证据——这符合 abstain 语义（不该编证据），可不改；但 GO-LOCK/RUNTIME-STALL 应在证据不足时仍引用已采集证据说明「为什么不足」。

### 6. 范围/拓扑类（PARTITION 61.1、CROSS-WORKER 64.7）

网络分区和跨 Worker 双根因案例部分命中（位置对但分类错）。这两个是「证据有了但归因粒度不够」——归到「网络/共享资源」却没能说清是分区还是调度。补「网络分区 vs 普通丢包」的区分信号（如丢包率/重传/连接超时模式）可提升。

---

## 四、不建议动的部分（已经很强）

- **abstention 100%**（18/18）：冲突证据、范围缺失、陈旧证据等 7 个鲁棒性案例全部正确拒答——保持。
- **unsafe 0**：安全处置零失误——保持现有「注册探针白名单 + 人工批准 R2 + 回滚」机制。
- **轨迹 100%**：运行时审计覆盖满分——保持。
- **健康/短暂波动案例**（NEG-*）：都命中，无需改。

---

## 五、预期收益汇总

| 改进项 | 改动量 | 预期严格根因 + | 预期平均分 |
|---|---|---|---|
| ① 探针选择补 runtime_snapshot | 小（症状→探针映射） | +3 案例（GO/RUNTIME/LATENCY） | 50→85 区间 |
| ② 下游可达性探测 + 下游归因 | 中（新探针 + 分析器） | +2 案例（PAYMENT/NOISY-DOWN） | 45→80 区间 |
| ③ root_entity 填充 | 小 | 实体命中 0→2 | +少许 |
| ④ 一致性收敛 | 中 | 不直接加 | 可信度 |
| ⑤ 证据引用补全 | 小 | — | +3~5 分/项 |

**先做 ① ③**（小改动、确定性收益），再做 ②，最后 ④⑤。做完 ①②③，严格根因率预计从 46.7% 提升到 **60-65%**，平均分从 78.6 到 **85+**。
