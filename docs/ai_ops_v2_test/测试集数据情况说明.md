# AI 运维诊断对比评测集 v2 —— 数据情况说明

> 评测完成日期：2026-08-11 ｜ 运行环境：Hyper-V 三节点虚拟机集群
> 本目录包含完整测试集、评测脚本、90 轮运行记录与逐轮审计包，可供同学复现测试和数据对比。

---

## 1. 这是什么

`ai_ops_v2` 是一套用于**比较不同 AI 运维诊断实现**的评测集。评测目标是：给定一个故障症状描述和采集范围，被测系统需自主完成「环境确认 → 证据采集 → 根因推理 → 可审计结论 → 安全处置」全流程。

- 公共数据（`benchmarks/ai_ops_v2/public/cases.json`）：只含用户可见症状和范围提示，可交给被测系统。
- 私有 Oracle（`benchmarks/ai_ops_v2/private/oracles.json`）：只由评测方保存，含故障注入、预期根因、必需证据和恢复条件，**不会传给被测系统**。
- `manifest.json`：固定案例清单、重复次数和指标口径。

## 2. 测试集规模与分类

**30 个案例 × 3 次重复 = 90 轮**，运行顺序由 `seed=20260811` 随机打乱。

| 轨道 | 数量 | 说明 |
|---|---|---|
| 单故障（live_single_fault） | 16 | CPU、延迟、Redis、支付、噪声 CPU、宿主机 I/O、宿主机内存、网络分区、OOM、磁盘耗尽、Java/Go/Python 锁、内存增长、运行时停顿、网络丢包 |
| 复合故障（live_compound_fault） | 7 | 内存+锁、磁盘+网络、噪声邻居+下游故障、OOM 重复恢复、跨 Worker 双根因、支付+Redis、历史噪声+当前故障 |
| 健康与鲁棒性（negative_and_robustness） | 7 | 健康、短暂波动、陈旧证据、重复证据、采集失败、冲突证据、范围缺失 |

## 4. 评测协议

每轮依次执行：

1. 环境确认（服务全部 1/1、前端 HTTP 200）
2. 故障注入（含 240 秒自动停止上限；磁盘耗尽用 192 MiB loopback 文件系统；网络丢包用独立 netns）
3. 创建诊断会话 → 系统自主选择探针 → 最多批准一个 R2 探针
4. 导出审计包（`/api/v1/diagnoses/{id}/audit-bundle`）
5. 精确回滚 + 恢复探活（12 服务 1/1 + 首页 200）

故障进程/容器全部带自动停止上限；私有 Oracle 全程不进入被测系统上下文。

### 5.3 未命中根因的主要模式（供改进）

逐包分析 90 个审计包后，未命中案例集中在三类模式：

1. **运行时类未采集 `runtime_snapshot`**（GO-LOCK 48.4 / RUNTIME-STALL 49.8 / LATENCY 52.6）
   这些案例的 oracle 要求 `runtime_snapshot` 证据（goroutine / 线程状态），但系统探测计划只跑了 sys_metrics + log_scan + perf_cpu，没有运行时快照 → 证据不足 → abstain。
   **对照组**：`PYTHON-LOCK`（94.7 命中）正确采集了 `runtime_thread_snapshot` 并识别为 `runtime_lock_contention`。同一类锁故障，Go 案例未命中纯粹是探针选择策略缺陷。

2. **下游依赖分析缺失**（PAYMENT 46.0 / NOISY-DOWNSTREAM 44.2）
   `payment_pause` 是 `docker pause paymentservice`（下游故障），系统要么 abstain、要么误判为同宿主 I/O 争用，说明缺少下游可达性探测与依赖归因。

3. **根因实体识别缺失**（root_entity 0/2）
   只有 2 个案例指定了根因实体（如 `paymentservice`、`redis-cart`），均未命中，是明确的独立短板。

## 6. 复现运行（同学侧）

### 6.1 前置条件

- 三节点 Hyper-V VM 集群（配置见 `benchmarks/environments/hyperv_online_boutique_verified_vm.json`）
- VM 上已部署被测系统 + Online Boutique v0.8.0（离线镜像 bundle）
- 本地 Python 3.9+，安装 `paramiko`

### 6.2 运行评测

```powershell
cd <仓库根目录>
$env:MINI_DROP_VM_PASSWORD = '<VM 密码>'
python docs\\ai_ops_v2_test\\scripts\\run_ai_ops_v2_vm.py --repetitions 3 --seed 20260811 `
  --output-dir reports\eval\<你的版本目录>
```

- 用相同的 `seed=20260811` 才能与本结果做配对比较。
- 中途可用 `Ctrl+C` 停止，再用 `--resume` 续跑；意外中断后先跑 `--cleanup-only` 确认环境健康再续跑。
- 注意：长任务建议用独立进程启动（PowerShell `Start-Process`），避免被终端会话回收。

### 6.3 评分

```powershell
python docs\\ai_ops_v2_test\\scripts\\evaluate_diagnosis_bundles.py `
  --dataset docs\\ai_ops_v2_test\\benchmarks\\ai_ops_v2 `
  --diagnosis-map reports\eval\<你的版本目录>\diagnosis-map.json `
  --bundle-dir reports\eval\<你的版本目录>\bundles `
  --output-dir reports\eval\<你的版本目录>\scored
```

### 6.4 与本次结果对比

```powershell
python docs\\ai_ops_v2_test\\scripts\\compare_diagnosis_evaluations.py `
  你的版本\scored\evaluation.json `
  docs\\ai_ops_v2_test\\evaluation_results\\evaluation.json `
  --left-name 你的版本 --right-name 当前版本 `
  --output comparison.json
```

对比时优先看：严格根因准确率、正确拒答率、根因实体命中、证据引用、轨迹覆盖、不安全动作、回滚成功率、McNemar 配对检验。

## 7. 本次实测暴露的产品缺陷（记录）

评测过程中发现并修复了一个真实缺陷：

- **`OB-ROBUST-CONFLICT-001`（冲突证据）409 硬失败**：`_build_target_scope` 对同一 `instance_id` 声明多个进程身份时抛 `ValueError` → HTTP 409，诊断从未创建。设计意图是系统应 **abstain**。已修复为将冲突实例排除 → 返回 unresolved scope → `NEEDS_SCOPE_CONFIRMATION`（正确拒绝作答）。修复后该案例 3 轮全部命中 abstention（40/40 根因分）。

修复位置：`server/app/diagnosis/orchestrator.py` `_build_target_scope`；配套测试 `tests/test_diagnosis_orchestrator.py::test_conflicting_instance_identity_abstains_instead_of_409`。
